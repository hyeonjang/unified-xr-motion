\subsection{Trigger Manager}\label{sec:motiontrigger}

Across XR deployments, avatar positioning and movement are governed by transforms across multiple coordinate spaces. 
These include the spawn point, the play space, and the tracking space defined relative to the main camera.
Our architecture implements this pattern with a Trigger Manager design.
The Trigger Manager keeps a registry of Motion Triggers, manages their lifecycle, and orchestrates their execution during runtime updates. 
Each Motion Trigger handles transforms in its assigned space, responds to spatial changes, and starts the relevant processing pipelines.

\subsubsection{Tracking Manager and SDK Integration}
At the tracking input layer, vendor SDKs feed Tracking Device Handlers.
The Handlers abstract vendor specifics and encapsulate interfacing complexity; new devices integrate by implementing a single interface per device type.
Where applicable, a handler converts vendor-specific data into a unified 6DoF pose in tracking space by normalizing every sample to a left-handed, Z-forward frame before handing it off.
For hand tracking, we anchor the hand-root frame at the wrist and set local axes as X→the index-finger direction, Y→outward palm normal, and Z→middle finger.
{\bf Table~\ref{tab:sdk-support-list}} lists supported modalities and per-SDK conversions; we provide handlers for controllers, XR trackers, hand tracking, and body tracking.
For example, Meta’s OVR SDK provides 3DoF joint rotations in a right-handed, X-forward local frame; the handler converts right- to left-handed with a Z-flip, remaps X-forward to Z-forward, and applies forward kinematics to reconstruct 6DoF joint poses.
Video-based tracking solutions (e.g., Mediapipe) only provide tracking-space 3DoF joint positions without rotations, so the handler estimates rotations by fitting coordinate frames to outgoing joint direction along each finger chain.
{\bf Table~\ref{tab:xr-hand-sdk-comparison}} summarizes per-SDK formats and conversion strategies.

The Tracking Manager keeps a roster of these handlers, reacts to their lifecycle events, and aggregates their normalized outputs into the Kinematic Buffer. 
It remains isolated as an independent subsystem to maximize input fidelity and extensibility while exposing a stable interface that allows flexible source composition and keeps the motion pipeline loosely coupled. 

\subsubsection{Support Root Motion}
Root motion drives avatar locomotion independently of tracking signals.
We make this separation explicit with a Waypoint Manager that implements the Root Motion Node interface.
It generates waypoint-based root-motion control data consumed by downstream motion processing and maintains independent coordinate spaces for movement.
